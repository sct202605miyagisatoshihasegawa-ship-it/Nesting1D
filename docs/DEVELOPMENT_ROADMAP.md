# Nesting1D 開発ロードマップ

- プロジェクト名：Nesting1D
- 対象：一次元ネスティングWebアプリ
- 開発方針：細かい人間確認を減らし、自動テストと開発ログを活用する
- 想定する主要な人間チェック回数：7回
- 将来構想：スマートフォン向けPWA化、計算ロジックのJavaScript移植

---

## 1. 開発の基本方針

本開発では、メソッド単位・画面部品単位の細かい確認を繰り返さず、  
**壊れやすい境界と、利用者にしか判断できない部分だけを人間が確認する。**

細かな実装確認は、Codexによる以下の作業で代替する。

- 自動テスト
- 静的確認
- 変更差分の確認
- 実装理由の記録
- 仕様との対応関係の記録
- 未解決事項の記録

人間は、計算結果の妥当性、画面の分かりやすさ、現場での使いやすさ、最終的な安全性を確認する。

---

## 2. 開発時に必ず残す記録

以下の3ファイルを `docs/` 配下に置き、開発中に継続更新する。

```text
docs/
├─ DEVELOPMENT_LOG.md
├─ DECISIONS.md
└─ TEST_RESULTS.md
```

### 2.1 DEVELOPMENT_LOG.md

時系列の開発記録。

記録内容：

- 実装した内容
- 実装理由
- 採用した設計
- 仕様との対応関係
- 変更したファイル
- 実行したテスト
- テスト結果
- 未解決事項
- 将来JavaScriptへ移植する際の注意点

### 2.2 DECISIONS.md

仕様判断・設計判断の記録。

記録例：

- 残材と廃棄材の境界
- 鋸刃厚の計算方法
- 同一パターンの定義
- 在庫モードの使用優先順位
- 同点候補の決定規則
- 保存方式
- エラー時の扱い

### 2.3 TEST_RESULTS.md

自動テストと人間確認の結果を記録する。

記録内容：

- チェック番号
- 確認日
- 確認対象
- 確認結果
- 不具合
- 修正後の再確認結果
- 保留事項

## 3. Codexへの共通指示

各開発作業では、原則として次の指示を含める。

```text
指定された機能群をまとめて実装してください。

実装途中の細かい人間確認は求めず、
指定されたチェックポイントまで自動テストで確認してください。

各実装について、以下を記録してください。

- 何を実装したか
- なぜその実装方法を選んだか
- 要件定義のどの項目に対応するか
- 変更したファイル
- 実行したテスト
- テスト結果
- 未解決事項
- 将来JavaScriptへ移植する際の注意点

記録先：
- docs/DEVELOPMENT_LOG.md
- docs/DECISIONS.md
- docs/TEST_RESULTS.md

プロジェクト外への書き込み、
無関係なファイル変更、
無断削除、
全面書き換え、
秘密情報の保存、
不要な外部通信は行わないでください。
```

# 4. 開発フェーズと人間チェック

## チェック1：要件・計算式の確定

### 実施時期

本格実装を開始する前。

### 実装側で準備するもの

- 計算ルール一覧
- 手計算用の代表例
- 境界値の例
- 期待する入力JSON
- 期待する結果JSON

### 人間が確認する内容

- 母材は左端から右方向へ切断する
- 右側からの切断は考えない
- 新品母材・既存残材ともに左端捨て切りを行う
- 左端捨て切りは `10mm + 鋸刃厚`
- その後は部材1本の切断ごとに鋸刃厚1回分を消費する
- 切断後の残りが0mmなら使い切り
- 切断後の残りが1～50mmなら廃棄材
- 切断後の残りが51mm以上なら残材
- 残材・廃棄材の境界は鋸刃厚に依存しない
- 今回必要な部材に使えない長さでも残材として記録する
- 同一パターンの定義
- 在庫モードの使用優先順位
- 同じ入力に対して同じ結果になる規則

### 完了条件

代表的な計算例について、手計算と期待結果が一致する。

## チェック2：計算エンジン完成

### 実施時期

画面実装の前。

### 実装対象

- 入力モデル
- 出力モデル
- 基本ネスティング処理
- パターン集約
- 残材・廃棄材判定
- 必要母材算出モード
- 在庫母材・残材活用モード
- 同点候補の決定規則
- 再現性
- 自動テスト

### 自動テストで確認する内容

- 基本計算
- 複数母材
- 複数寸法
- 同一寸法の集約
- 鋸刃厚
- 左端捨て切り
- 残材判定
- 廃棄材判定
- 母材を超える部材の拒否
- 0・負数・文字入力
- 同じ入力で同じ結果
- 同一パターン集約
- 在庫優先順位

在庫優先順位：

```text
使用可能な既存残材
↓
保有している新品母材
↓
追加購入する新品母材
```

### 人間が確認する内容

- 代表例の結果
- 想定外に母材本数が増えていないか
- 切断パターンが極端に細分化されていないか
- 現場感覚として不自然な結果がないか

### 完了条件

自動テストがすべて成功し、代表例の結果が妥当である。

## チェック3：入力画面と計算接続

### 実装対象

- 計算ボタン

### 人間が確認する内容

- 入力しやすいか

- エラー内容が理解できるか
- スマートフォン幅でも最低限操作できるか
- 計算までの操作手順が多すぎないか

### この時点で確認しないもの

- 色の微調整
- フォントの細部

# 5. 想定チェック回数

主要な人間チェックは、原則として以下の7回とする。

| 回 | 確認内容 |
|---:|---|
| 1 | 要件と計算式 |
| 2 | 計算エンジン |
| 3 | 入力画面と計算接続 |
| 4 | 結果画面と現場モード |
| 5 | JSON・HTML・再読込 |
| 6 | 実務想定の通し操作 |
| 7 | リリース前最終確認 |

大きな仕様変更や重大な不具合が発生した場合でも、  
追加確認を含めて **7～9回程度** を目安とする。

---

# 6. 手戻りを減らすための重要ルール

1. 画面より先に計算エンジンを完成させる  
2. 計算エンジンはFastAPIや画面に依存させない  
3. 入力と出力をJSONで固定する  
4. 計算例を自動テストとして保存する  
5. 仕様変更はDECISIONS.mdへ記録してから実装する  
6. 人間確認では途中修正せず、問題をまとめて記録する  
7. UIの細かな装飾は機能完成後にまとめて行う  
8. 同じ入力に対して同じ結果を返す  
9. 将来のJavaScript移植を妨げるPython固有依存を計算ロジックへ持ち込まない  
10. リリース前に新しい環境から再構築する  

---

# 7. 将来のJavaScript移植を見据えた構造

初期版：

```text
Webブラウザ
↓
HTML / CSS / JavaScript
↓
FastAPI
↓
Python計算ロジック
↓
結果JSON
```

将来：

```text
スマートフォン
↓
PWA
↓
JavaScript計算ロジック
↓
ローカル保存
```

そのため、初期版から次を守る。

- 計算ロジックは純粋関数に近い形とする
- ファイル保存を計算処理へ直接含めない
- HTTP処理を計算処理へ含めない
- 入出力スキーマを明確にする
- Python版とJavaScript版で共通のテストデータを使えるようにする
- 計算結果JSONへ形式バージョンを持たせる

# 8. 完成の定義

初期版は、以下を満たした時点で完成とする。

- 必要母材算出モードが使用できる
- 在庫母材・残材活用モードが使用できる
- 切断条件が正しく反映される
- 同一パターンが集約される
- 現場向け切断手順が表示される
- JSON保存・再読込ができる
- HTML出力・印刷ができる
- エラー時に異常終了しない
- 同じ入力で同じ結果になる
- 自動テストがすべて成功する
- リリース前確認が完了している
