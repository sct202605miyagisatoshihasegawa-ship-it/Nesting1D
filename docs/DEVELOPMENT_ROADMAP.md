## 1. 開発の基本方針

開発は、メソッド単位や画面部品単位で人間確認を繰り返すのではなく、機能群をCheckpoint単位でまとめて進めた。細かな実装確認は、次の作業を中心に実施した。

- 自動テスト
- 静的確認
- 変更差分の確認
- 実装理由と仕様との対応関係の記録
- 未解決事項の記録

人間確認は、計算結果の妥当性、画面の分かりやすさ、現場での使いやすさ、実ブラウザでの一連操作など、人間による判断が必要な境界へ集約した。

実装順は、要件と計算式、計算エンジン、Web入力、結果表示、入出力、実務想定の通し操作、リリース前確認とした。計算ロジックをWeb・画面・HTTP処理から分離し、画面実装より先に自動テスト可能な計算エンジンを整備した。

## 4. 開発フェーズと人間チェック

### Checkpoint 1：要件・計算式の確定

本格実装前に、計算ルール、手計算用の代表例、境界値、入出力データ構造を準備した。確認対象は次のとおりである。

- 左端から右方向へ切断する。
- 新品母材・在庫残材の使用開始時に、左端捨て切り寸法と鋸刃厚1回分を消費する。
- 部材1本の切出しごとに鋸刃厚1回分を消費する。
- 残り0mmを使い切り、1～50mmを廃棄材、51mm以上を残材とする。
- 残材境界へ鋸刃厚を加算しない。
- 同一パターンの定義と、決定的な結果選別を定める。

代表例と境界条件を後続の計算エンジンテストの基準として使用した。左端捨て切り寸法は固定値ではなく入力条件とし、V1.0.1では0～100mmの範囲で扱う。

### Checkpoint 2：計算エンジン完成

画面実装前に、次の計算機能と自動テストを整備した。

- 入力・出力モデル
- 基本ネスティング処理とパターン集約
- 残材・廃棄材判定
- 必要母材算出モード
- 在庫母材・残材活用モード
- 複数候補の生成と段階的・辞書式の選別
- 同点候補を決定する安定キー
- 同一入力に対する再現性
- 基本計算、複数母材、複数寸法、鋸刃厚、左端捨て切り、境界値、異常値のテスト

開発初期には在庫残材、在庫新品材、追加購入新品材という処理順も確認項目としていた。完成版では単純な固定使用順を最終選別規則とはせず、生成した候補を完全充足、追加購入新品材数、廃棄材量、残材量、残材本数、パターン数、寸法変更回数、安定キーの順で比較する方式へ確定した。

計算ロジックはFastAPI、HTTP処理、画面表示から分離した。完全な数学的最適解の保証ではなく、決定的な候補生成・選別によって現場で実行しやすい計画を提示する方式を採用した。

### Checkpoint 3：入力画面と計算接続

Web画面から計算エンジンを呼び出せる段階で、次を実装・確認した。

- 2つの計算モードの選択
- 共通情報と切断条件の入力
- 必要部材行と在庫残材行の追加・削除
- 在庫新品材の入力
- HTML、JavaScript、Pydantic、フォームPOSTによる入力検証
- 計算実行とエラー表示
- PCの2カラムとスマートフォン幅の1カラム表示

両モードで画面入力から計算まで進める状態とした。入力制限は開発後半のV1.0.1最終化で、すべての入力経路を同じ値へ統一した。

### Checkpoint 4：結果画面と切断手順

主要な結果表示として、切出し部材、購入新品材、在庫新品材、在庫残材、発生残材、廃棄材、集約した切断パターン、切断手順、管理情報を整備した。

開発初期に想定した「ダッシュボード」「パターン一覧」「母材一覧」「現場モード」という複数画面構成は採用せず、完成版では入力と結果を同一画面内で確認できる構成へ整理した。最終目視ではPCとスマートフォン幅の双方で表示と操作を確認した。

### Checkpoint 5：JSON・HTML出力と再読込

計算後の管理・出力機能として、次を実装・確認した。

- 管理番号の発行と再計算時の識別情報管理
- JSONとHTMLの独立出力
- ブラウザFile APIによる端末JSON読込と再計算
- 不正JSONと読込上限の検証
- HTMLエスケープ、UTF-8、CSS内包のHTML出力
- JSONとHTMLにおける同一管理番号の使用
- `Cache-Control: no-store`
- サーバーへ利用者データを永続保存しないこと

開発途中にはサーバー保存方式も実装・検討したが、公開版V1では撤去した。完成版ではJSON・HTMLをリクエスト処理中に生成して端末へ直接ダウンロードし、端末JSONはブラウザ内で読み込む。JSONファイル本体、入力内容、計算結果、出力ファイル、計算履歴をサーバーへ永続保存しない。

2026-08-05の実ブラウザ確認で、JSON・HTMLの独立出力、File API読込、旧保存APIへの通信がないこと、サーバー上の保存領域が増加しないこと、PC・スマートフォン配置を確認した。V1.0.1最終確認ではHTML出力と、左端捨て切り・鋸刃厚の表示反映も再確認した。

### Checkpoint 6：実務想定の通し操作

主要機能の完成後、途中で細かな修正を挟まず、入力から出力・再読込までを一連で操作した。

```text
必要部材、在庫、切断条件を対象モードに応じて入力
↓
計算
↓
材料内訳、在庫使用結果、発生残材・廃棄材を確認
↓
切断手順を確認
↓
JSON・HTMLを端末へ出力
↓
端末JSONを再読込
↓
再計算
```

両モードについて、入力、計算、結果表示、端末出力、端末JSON再読込の流れを確認した。最終目視ではPCとスマートフォン幅の双方で入力・計算・結果表示が正常に動作した。

### Checkpoint 7：リリース前最終確認

機能実装、公開環境検証、V1.0.1最終調整の完了後、次を確認した。

- 全自動テスト
- 不正入力とHTTPリクエスト本文サイズ境界
- Cloud Run上の単発・並列実行、再現性、タイムアウト安全域
- production環境のAPI文書非公開、`robots.txt`、noindex、セキュリティヘッダ
- サーバー永続保存および不要な外部通信がないこと
- Git管理対象に秘密情報、個人パス、不要な生成物がないこと
- PCとスマートフォン幅の最終目視
- JSON・HTML出力と端末JSON読込
- 仕様、設計判断、開発履歴、試験結果の文書整合
- `git diff --check` とworking treeの確認

2026-08-10に全244テスト成功、PC・スマートフォン幅の最終目視、HTML出力、入力数値フォント調整後の表示を確認した。GitHub公開前監査とdocs棚卸しも実施し、V1.0.1のコードを凍結した。

当初のリリース前候補には、Dockerでの新規起動、依存関係の再構築、README記載手順による起動、印刷の個別確認も含まれていた。参照した開発履歴・試験結果には、これらすべてを2026-08-10の独立した最終試験として実施した記録まではないため、本書では推測で最終完了実績に含めない。Cloud Runのコンテナ実環境試験およびHTMLのブラウザ表示は別途確認済みである。

## 5. Checkpoint後のV1.0.1最終化

### 5.1 Cloud Run公開環境検証

Cloud Run上で、代表入力の単発実行、6並列実行、出力のSHA-256一致、60秒タイムアウトに対する安全域、HTTP本文サイズ境界、production向けセキュリティ設定を検証した。詳細な条件と結果は `TEST_RESULTS.md` に記録した。

### 5.2 入力上限と表示の最終化

V1.0.1では、実務上の想定範囲へ入力制限を統一した。

- 必要部材：最大20行
- 在庫残材：最大10行
- 必要部材1行、在庫残材1行：1～500本
- 在庫新品材：0～500本
- 母材長、必要部材寸法、在庫残材寸法：1～6100mm
- 鋸刃厚、左端捨て切り：0～100mm
- 独立した合計必要本数1,000,000本制限を廃止
- 入力構造上の最大必要本数：20行 × 500本 = 10,000本

HTML、JavaScriptのローカルJSON読込、Pydanticモデル、フォームPOST検証を同じ制限へ統一し、受理値と拒否値の境界試験を追加した。表示用viewへ検証済みの左端捨て切り値と鋸刃厚を渡すよう修正し、Web画面とHTML出力への反映を確認した。

節目のコミットは `732989c Finalize V1.0.1 input limits` である。

## 6. 開発方法として維持した原則

1. 要件と計算式を確認してから実装する。
2. 画面より先に計算エンジンを整備する。
3. 計算ロジックをFastAPI、画面、HTTP、ファイル出力から分離する。
4. 入出力データ構造と形式バージョンを明確にする。
5. 代表例、境界値、異常値、再現性を自動テストに残す。
6. 人間確認では途中修正を繰り返さず、問題をまとめて記録する。
7. UIの細かな調整は主要機能の完成後に行う。
8. 同じ入力、同じアプリバージョン、同じ計算方式では同じ結果を返す。
9. 仕様変更時は仕様資料、設計判断、開発履歴、テストを同期する。
10. Gitの節目となるコミットで、Checkpointと公開版の状態を追跡できるようにする。
11. リリース前に自動試験、実ブラウザ確認、公開環境確認、差分確認を組み合わせる。

## 7. 開発初期に検討したV1.0.1対象外の構想

開発初期には、PWA化、オフライン動作、計算ロジックのJavaScript移植、ブラウザ内の永続保存を将来構想として検討した。これらはV1.0.1では実装しておらず、完成したV1.0.1の開発工程にも含めない。

一方、計算ロジックをWeb・HTTP・保存処理から分離し、入出力スキーマを明確にする設計は、テスト容易性と責務分離のためV1.0.1でも採用した。この採用理由は、未実装の将来構想を現在の予定として示すものではない。
