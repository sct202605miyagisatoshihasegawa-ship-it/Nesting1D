# Nesting1D 仕様・設計判断記録

## 2026-07-26：チェック1で確定した仕様

### 1. 左端捨て切り寸法
- 判断内容：利用者が変更可能、初期値10mm。入力値と鋸刃厚1回分を新品母材・既存残材の両方で消費する。
- 採用理由：現場条件に対応しつつ標準値を明確にするため。
- 却下した案：10mm固定。
- 影響範囲：入力検証、使用可能長、残材判定、切断手順、テスト。
- 将来見直す条件：材料種別ごとの値が必要になった場合。

### 2. 在庫モードの新品母材長
- 判断内容：保有新品母材と追加購入新品母材は同じ長さとし、入力は1種類。既存残材は寸法ごとに異なる長さを入力可能。
- 採用理由：初期版の入力と計算を明快にするため。
- 却下した案：複数種類の新品母材、保有材と購入材への別々の長さ入力。
- 影響範囲：在庫入力、候補生成、追加購入数、結果JSON。
- 将来見直す条件：複数種類の新品母材対応時。

### 3. 旧仕様：候補内最少母材本数
- 判断内容：数学的完全最適は保証しない。探索で生成した候補中、母材使用本数が最も少ない候補を優先。同数ならパターン数、寸法変更回数の順に減らす。文書では「候補内最少母材本数」と表現する。
- 採用理由：実用的な探索時間を保ち、完全最適との誤解を避けるため。
- 却下した案：完全最適保証、パターン集約のため候補内最少本数を超える案。
- 影響範囲：候補生成・比較、結果説明、再現性、テスト。
- 将来見直す条件：探索方式変更、または許容増加本数を設定可能にする時。

### 4. 入力上限
- 判断内容：寸法最大1,000,000mm、鋸刃厚・捨て切り最大10,000mm、1行最大100,000本、必要部材・既存残材は各最大1,000行、合計必要本数最大1,000,000本。通常利用目標は合計1,000本程度。
- 採用理由：異常な処理時間・メモリ消費を防ぎ、通常利用へ余裕を持たせるため。
- 却下した案：上限なし、通常利用目標を上限とする案。
- 影響範囲：入力モデル、検証、エラー、境界値・性能テスト。
- 将来見直す条件：実測性能または利用実績から調整が必要な時。

### 5. 旧仕様：日時と管理番号
- 判断内容：`Asia/Tokyo` を使用。初回保存日の日本時間で、同日既存番号の最大値+1を採番。同名なら再確認して次番号を採番。初回保存だけ新規採番し、上書きでは維持。JSONとHTMLは同じ番号。
- 採用理由：現場の日付と一致させ、重複を避け、出力間の対応を維持するため。
- 却下した案：UTC日付、保存ごとの再採番、形式ごとの別番号。
- 影響範囲：保存、ファイル名、JSON・HTML、保存テスト。
- 将来見直す条件：複数利用者・プロセスの同時保存対応時。

### 6. 旧仕様：在庫モードの候補優先順位
- 判断内容：必要部材の充足、追加購入新品母材数の抑制、既存残材活用の順。残材使用で追加購入数が増えるなら使わない。追加購入数が同じなら既存残材を多く使う候補を優先し、その後は保有新品、追加購入新品の順。基本表示順は「使用可能な既存残材→保有新品母材→追加購入新品母材」。
- 採用理由：充足と購入抑制を守りながら残材を活用するため。
- 却下した案：追加購入数が増えても残材を必ず使う案。
- 影響範囲：候補評価、材料一覧、切断手順、追加購入数、テスト。
- 将来見直す条件：評価重みを設定可能にする時。

### 7. 使用不能な既存残材
- 判断内容：数値として正しい残材が捨て切り後に必要部材を1本も切り出せなくても全体をエラーにしない。未使用在庫とし、未使用理由を表示。0以下、文字、小数、上限超過は入力エラー。
- 採用理由：正当な在庫情報を保持し、計算可能な材料で処理を継続するため。
- 却下した案：使用不能残材が1件でもあれば全体を拒否する案。
- 影響範囲：入力検証、在庫分類、未使用理由、結果JSON、テスト。
- 将来見直す条件：在庫の事前整理を必須にする時。

### 8. 旧仕様：将来の許容本数設定
- 判断内容：初期版では候補内最少母材本数からの増加を許容しないが、将来変更可能な余地を残す。
- 採用理由：初期版を単純にし、将来の段取り優先運用へ備えるため。
- 却下した案：初期版から許容本数を入力する案。
- 影響範囲：候補比較、将来の設定・スキーマ。
- 将来見直す条件：母材追加と段取り削減の交換条件を指定する要望が生じた時。

### 9. 寸法変更回数
- 判断内容：同一パターン内部は異なる寸法数−1、初回設定は含めず、使用回数も掛けない。パターン間は前パターン末尾と次パターン先頭が異なる場合に1回加算する。実施順を変更回数が少なくなるよう決定し、同点順を固定する。
- 採用理由：同一パターンをまとめて加工する現場運用を反映するため。
- 却下した案：使用回数を掛ける案、初回設定を含める案、パターン間を無視する案。
- 影響範囲：候補比較、実施順、結果モデル、再現性テスト。
- 将来見直す条件：パターンをまとめて加工しない運用へ変わる場合。

### 10. 旧仕様：在庫モードの同点候補と使い切り
- 判断内容：充足、追加購入新品母材数、使用既存残材本数、既存残材からの切出合計長、使用後の既存残材合計長、新規残材の分散抑制、パターン数・寸法変更回数、固定決定順の順に比較する。残り0mmは残材・廃棄材に含めず `used_up`（使い切り）とする。
- 採用理由：既存残材を実質的に多く消費し、小残材を分散させず大きな再利用可能残材を確保するため。
- 却下した案：使用残材本数だけで同点とする案、残り0mmを廃棄材とする案。
- 影響範囲：在庫候補比較、残材分類、結果モデル、例6・7、回帰テスト。
- 将来見直す条件：残材価値を長さ以外の指標で評価する場合。

### 11. 未使用在庫の材料区分と理由
- 判断内容：未使用在庫へ`source_type`を持たせ、`existing_remnant`と`held_new_stock`を区別する。必要部材充足後は`NOT_NEEDED`、残っている必要部材を捨て切り後に1本も切れない場合だけ`NO_REQUIRED_PART_FITS_AFTER_TRIM`とする。切出可能な既存残材を使用しない候補には`NOT_SELECTED_BY_CANDIDATE_SELECTION`を設定し、その候補が最終選択された場合に結果へ出力する。
- 採用理由：未使用材料の種類と未使用になった原因を利用者が誤解なく確認できるようにするため。
- 却下した案：必要数が0の材料を寸法不足として扱う案、画面側で理由を推測する案。
- 影響範囲：計算結果の`unused_inventory`、在庫結果画面、理由コード回帰テスト。
- 将来見直す条件：未使用在庫へ識別番号や材料固有情報を持たせる場合。
- 非影響範囲：候補比較、母材割り当て、追加購入数、完成数、パターン集約、残り0mmの`used_up`。

### 12. 旧仕様：初期版の正式保存と端末ダウンロード
- 判断内容：正式保存はプロジェクト内`data/`限定でJSONとHTMLを保存し、成功時だけ保存済みとする。端末向けJSON・HTMLダウンロードはコピー取得とし、保存済み判定を変更しない。File System Access APIは初期版で採用しない。アプリ内の破棄を伴う操作は保存・破棄・キャンセル、ブラウザ離脱は標準確認を使用する。
- 採用理由：管理番号、競合回避、安全な置換をサーバー側で保証しつつ、PC・スマートフォンへコピーを取得可能にするため。
- 却下した案：利用者によるサーバー絶対パス入力、ブラウザダウンロードだけを正式保存とする案、初期版のFile System Access API。
- 影響範囲：保存層、Web API、画面、未保存状態、`data/`のGit除外、保存・出力テスト。
- 将来見直す条件：PWA化、対応ブラウザ限定の端末ファイル保存、専用Dockerボリュームへ移行する時。

### 13. 候補選別による未使用理由
- 判断内容：切出可能な既存残材を使用しない候補には理由コード`NOT_SELECTED_BY_CANDIDATE_SELECTION`を設定し、その候補が最終選択された場合に結果へ出力する。表示文言は「候補選別の結果、使用しない計画が選ばれたため未使用」とする。JSONにはコードだけを保存し、画面とHTMLでは表示層が日本語文言へ変換する。
- 採用理由：従来の理由は追加購入新品母材数だけを示していたが、新しい候補選別では廃棄材総量、残材総量、残材本数、パターン数、寸法変更回数、最終決定キーによっても残材不使用候補が選ばれるため。
- 却下した案：追加購入抑制だけを表す理由の継続、候補ごとの評価詳細を理由コードへ埋め込む案。
- 影響範囲：候補生成、計算結果の`unused_inventory`、JSON保存、Web表示、HTML出力、テスト。
- 将来見直す条件：選択理由の内訳を利用者へ個別表示する要件が追加された場合。

### 14. 現行の候補生成・選別順位
- 判断内容：必要母材算出モードは2候補、在庫モードは4候補を生成し、完全充足、追加購入新品母材数、廃棄材総量と許容値、残材総量と独立許容値、残材本数、パターン数、寸法変更回数、安定キーの順で選別する。許容値の既定値は両方0mmとし、候補生成順は判定基準にしない。
- 採用理由：材料効率と作業性を段階的に比較し、加重点なしで判断根拠と再現性を保つため。
- 却下した案：旧来の既存残材使用本数優先、加重点評価、生成順による最終決定。
- 影響範囲：`SelectionCandidate`、`select_candidate()`、engine接続、固定結果、テスト、計算規則。
- 将来見直す条件：廃棄材・残材許容値の本採用値や新しい評価項目を確定する場合。

### 15. 完全同値候補の未使用理由
- 判断内容：未使用理由は、必要部材確保済みなら`NOT_NEEDED`、残需要があり物理的に1本も切れなければ`NO_REQUIRED_PART_FITS_AFTER_TRIM`とする。切出可能な既存残材を使用しない候補には`NOT_SELECTED_BY_CANDIDATE_SELECTION`を設定し、その候補が最終選択された場合に結果へ出力する。同じ物理状態には候補経路によらず同じ理由を付ける。
- 採用理由：reason_codeを安定キーへ含めず、完全同値候補の順序を反転してもCalculationResultを一致させるため。
- 却下した案：reason_codeを比較キーへ追加する案、Pythonの先頭同点候補へ依存する案。
- 影響範囲：未使用残材理由、候補順非依存性、JSON、Web、HTML、テスト。
- 将来見直す条件：材料固有の使用可否条件を追加する場合。


### 16. 残材・廃棄材の固定境界
- 判断内容：切断後の残り0mmは`used_up`、1mm以上50mm以下は`scrap`、51mm以上は`remnant`とする。分類境界は鋸刃厚に依存させない。
- 採用理由：ケース7の人間確認で鋸刃厚3mm時に51～53mmが廃棄材となる不整合を確認し、現場運用上の確定境界を計算結果と候補評価へ一貫して反映するため。
- 却下した案：廃棄判定境界へ鋸刃厚を加える既存方式、表示層だけで分類を補正する案。
- 影響範囲：`remainder_class()`、候補の`waste_length_mm`・`remnant_length_mm`・`remnant_count`、候補選択、CalculationResult、JSON・Web・HTML表示、境界テスト、計算規則文書。
- 非影響範囲：切出可否、`remaining_length()`、`used_length()`、未使用理由の日本語表示。
- 将来見直す条件：材料種別ごとに廃棄判定基準を変更する要件が追加された場合。


### 17. 公開版V1の非永続データ取り扱い
- 判断内容：サーバーは計算とメモリ内JSON・HTML生成だけを行い、利用者データを永続保存しない。端末JSONはFile APIで読み込み、旧保存API、保存一覧、再ダウンロード、`RecordStorage`、`data/`参照を公開版V1から撤去する。
- 採用理由：計算条件、管理情報、備考、結果に会社名・担当者名・案件情報が含まれ得るため、限定公開でもサーバーへ保持しない境界を明確にする。
- 却下した案：旧保存経路を互換機能として残す案、将来のデータベース化に備えて保存層を残す案。
- 影響範囲：Web API、画面操作、ブラウザ状態、JSON読込、テスト、`app/storage.py`、`data/`参照。既存`data/`実データそのものは自動削除しない。
- 将来見直す条件：V2以降で認証・利用者別保存・データベースの要件と安全対策を別途確定した場合。
- 移行時の不具合と解消：旧「保存」UI・APIと新しい端末出力経路が一時的に混在し、利用者操作で`data/`保存が継続する誤認・実動作が発生した。互換経路を残さず旧UI、旧API、`RecordStorage`を完全撤去して解消した。
- 人間確認：2026-08-05にJSON・HTML独立出力、状態表示、File API読込、旧API通信不存在、`data/`非増加、PC・スマートフォン配置を実ブラウザで確認し合格。

### 18. 公開版V1の機能境界・機能凍結・限定公開
- 判断内容：自動テストおよび人間による受入確認が完了したコミット`ac82ed5`（公開版V1の保存方式を端末直接出力へ移行）を公開版V1機能凍結の基準とする。凍結後は原則として新機能を追加しない。
- V1に含める計算機能：必要母材モード、在庫モード、在庫残材・在庫新品材・追加購入新品材、左端捨て切り・鋸刃厚・固定50mm境界、複数の貪欲的戦略による候補生成、段階的候補選別、決定的タイブレーク、未使用在庫と理由、発生残材・廃棄材・使い切りの分類。
- V1に含める画面・出力：ダッシュボード、パターン一覧、使用材料一覧、現場向け切断手順、未使用在庫、管理番号・件名・材料種類・データ製作者・備考、PC・スマートフォン対応、JSON・HTMLのメモリ内直接出力、HTMLのブラウザ印刷、File APIによる端末JSON読込、新旧管理番号互換、JSON・HTML間の識別情報・入力・結果の整合。
- データ取り扱い原則：判断17を公開版V1の境界として維持する。サーバーは計算と出力生成だけを行い利用者データを保持せず、端末JSON本体を送信しない。旧サーバー保存機能を互換目的や将来用途のために残さない。ブラウザ状態もデータベース、Cookie、`localStorage`等へ永続化せず、出力レスポンスのキャッシュを抑止する。
- V1に含めない機能：ログイン・認証・ユーザー管理・管理者画面・ユーザー別保存領域、データベース・サーバー保存・履歴・検索・上書き・再ダウンロード・端末JSONアップロード・共有・クラウド同期、完全最適解保証・大規模全探索・二次元／三次元ネスティング・複数材質／規格や複数設備の同時計算・原価計算、CSV／Excel／PDF直接入出力、大規模UI再設計、ページ再読込後の計算・出力状態復元。必要性と保守コストを再評価し、V2以降の候補とする。
- V1内で許可する変更：不具合修正、誤認や作業ミスを防ぐ表示修正、セキュリティ修正、公開環境で判明した問題への対応、既存仕様を保証するテスト・文書修正、依存関係や実行環境の必要最小限の保守修正。変更理由がこの範囲に該当することを事前に確認し、関連テストと必要な人間確認を行う。
- V2以降へ回す変更：利便性向上、新しい計算モード・入出力形式・保存方式、認証・ユーザー管理・データベース、大規模UI変更、アルゴリズム機能追加、対応規模の大幅な拡大。分類が難しい場合は実装前にV1の不具合修正かV2の機能追加かを確認する。
- 限定公開方針：少人数の試用日時を事前に決め、必要な時間帯だけ公開し、終了後はアプリまたはサーバーを停止する。URLは利用者へ直接共有し、検索エンジンへの積極掲載や一般・常時公開は行わず、V1にはログインを設けない。常時公開への移行は試用結果と安全対策の確認後に判断する。起動中は公開Webサービスとして扱い、HTTPS、入力・処理量制限、エラー秘匿、キャッシュ抑止、アクセス範囲を確認する。
- 採用理由：受入済みの機能と非保持方針を安定させ、限定試用前の変更を安全性・品質維持に必要な範囲へ限定するため。
- 却下した案：V1へ利便性向上を継続追加する案、将来の認証・データベース化を理由に旧保存責務を残す案、不特定多数へ常時公開する案。
- 影響範囲：V1の変更判断、レビュー、テスト、人間確認、限定公開運用、V2候補管理。コード、UI、計算処理、入出力仕様への変更はない。
- 将来見直す条件：限定試用結果と安全対策を確認して常時公開またはV2の要件定義へ進む場合。
