# Nesting1D V1.0.1 仕様・設計判断記録

- 対象アプリバージョン：1.0.1
- JSON形式バージョン：1.0
- 更新日：2026-08-10

この文書は、Nesting1Dで現在採用している仕様・設計と、その採用理由を記録する。

- 現在の詳細仕様は `REQUIREMENTS.md` を正とする。
- 実装時期と変更内容は `DEVELOPMENT_LOG.md` に記録する。
- 試験方法と結果は `TEST_RESULTS.md` に記録する。
- 本文で「廃止済み」と明記した判断は履歴であり、V1.0.1の現行仕様ではない。

---

## 1. 一次元材料と加工条件を計算単位にする

- 状態：現行
- 判断内容：長さだけで表す一次元材料を対象とし、同時に使用できる同一の材質・規格・加工条件の材料を1回の計算単位とする。
- 採用理由：切断条件が異なる材料を同一計画へ混在させず、結果を現場でそのまま確認できる単位に保つため。
- 却下した案：二次元・三次元材料、複数材質・複数規格・複数設備を同時に最適化する案。
- 影響範囲：入力構造、計算モード、結果表示、利用上の注意。

## 2. 左端から切断し、使用開始時に左端捨て切りを行う

- 状態：現行
- 判断内容：新品母材、在庫新品材、在庫残材を左端から右方向へ切断し、右端捨て切りは行わない。各材料の使用開始時に「左端捨て切り寸法 + 鋸刃厚1回分」を消費し、部材1本の切出しごとに鋸刃厚1回分を消費する。在庫残材の再使用にも同じ規則を適用する。
- 採用理由：材料種別によって加工規則を変えず、実際の切断順と消費長を一貫させるため。
- 却下した案：左端捨て切り10mm固定、在庫残材だけ捨て切りを省略する案、右端捨て切りを行う案。
- 影響範囲：使用可能長、切出可否、残り長さ、切断手順、入力検証。

## 3. 在庫新品材と追加購入新品材は同じ母材長を使う

- 状態：現行
- 判断内容：在庫新品材と追加購入新品材には1種類の新品母材長を共通使用する。在庫残材は行ごとに異なる寸法を入力できる。
- 採用理由：V1の入力と計算を明快にし、追加購入数と在庫使用数を同じ基準で比較するため。
- 却下した案：複数種類の新品母材長、在庫新品材と追加購入新品材へ別々の長さを設定する案。
- 影響範囲：在庫入力、候補生成、追加購入数、JSON形式。

## 4. 使用不能な在庫残材は入力エラーにせず理由付きで残す

- 状態：現行
- 判断内容：数値制約を満たす在庫残材が、左端捨て切り後に残っている必要部材を1本も切り出せなくても、計算全体をエラーにしない。未使用在庫として材料区分と理由を結果へ保持する。
- 採用理由：正当な在庫情報を失わず、使用可能な材料で計算を継続するため。
- 却下した案：使用不能な在庫残材が1件でもあれば入力全体を拒否する案、表示層が未使用理由を推測する案。
- 影響範囲：入力検証、未使用在庫、JSON、Web表示、HTML出力。

未使用理由は物理状態と候補選別結果から次のように決定する。

- 必要部材が確保済み：`NOT_NEEDED`
- 残需要があり、捨て切り後に1本も切り出せない：`NO_REQUIRED_PART_FITS_AFTER_TRIM`
- 切出可能だが候補選別で不使用計画が選ばれた：`NOT_SELECTED_BY_CANDIDATE_SELECTION`

同じ物理状態には候補経路によらず同じ理由を付け、理由コード自体を最終安定キーへ含めない。

## 5. 完全最適化ではなく、複数候補を段階的に選別する

- 状態：現行
- 判断内容：完全な数学的最適解や全組合せ探索を保証せず、限定した貪欲的戦略で複数候補を生成する。必要母材算出モードは寸法の降順・昇順による2候補、在庫モードはその2通りと在庫残材の使用・不使用を組み合わせた4候補を生成する。
- 採用理由：入力制限内で実用的な処理時間を保ちつつ、単一の貪欲順だけに結果を依存させないため。
- 却下した案：完全最適保証、大規模な全探索、利用者がアルゴリズムを切り替える案。
- 影響範囲：計算エンジン、候補生成、結果説明、性能、再現性。

候補は加重点評価を使わず、次の順に段階的・辞書式に比較する。

1. 必要部材を完全充足
2. 追加購入新品母材数を最小化
3. 廃棄材総量を最小化
4. 発生残材総量を最小化
5. 発生残材本数を最小化
6. 切断パターン数を最小化
7. 寸法変更回数を最小化
8. 決定的な安定キーで最終決定

廃棄材と発生残材の許容値は独立させ、V1.0.1ではどちらも0mmとする。

- 採用理由：評価項目の優先関係を明示し、重み調整による予期しない逆転を避け、判断根拠と再現性を保つため。
- 却下した案：既存残材の使用本数を常に優先する案、加重点評価、候補生成順を最終判定に使う案。

### 廃止済みの候補選別判断

開発初期には、次の判断を採用していた。

- 候補内で母材使用本数を最少にし、同数ならパターン数、寸法変更回数で比較する。
- 在庫モードでは追加購入数の次に既存残材の使用本数や切出合計長を優先する。
- 追加購入数が同じ場合は、既存残材、在庫新品材、追加購入新品材の順を強い優先順位として扱う。

これらは現行の段階的候補選別へ置き換えたため、V1.0.1の判断基準ではない。在庫残材を使用する候補と使用しない候補を比較し、物理的な材料処理順とは別に、上記8段階で最終計画を決定する。

## 6. 寸法変更回数はパターンをまとめて加工する前提で数える

- 状態：現行
- 判断内容：同一パターン内部の寸法変更回数は「異なる寸法数 - 1」とし、初回設定とパターン使用回数を含めない。パターン間は前パターン末尾と次パターン先頭が異なる場合に1回加算する。実施順は変更回数を抑えるよう決め、同点順を固定する。
- 採用理由：同一パターンをまとめて加工する現場運用を反映するため。
- 却下した案：パターン使用回数を掛ける案、初回設定を含める案、パターン間の変更を無視する案。
- 影響範囲：候補比較、パターン実施順、切断手順、再現性。

## 7. 決定的な安定キーで再現性を確保する

- 状態：現行
- 判断内容：同じ入力条件、同じアプリバージョン、同じ計算方式では同じ計算結果を返すことを基本とする。主要評価がすべて同値の場合だけ、使用材料の種別・元長・切断順・残り長さと、未使用材料の種別・長さ・本数を正規化した安定キーで最終決定する。
- 採用理由：Pythonの列挙順や候補生成順による偶発的な結果差を避けるため。
- 却下した案：最初に生成された同点候補をそのまま採用する案、未使用理由コードを比較キーに含める案。
- 影響範囲：候補選別、使用材料順、パターン番号、未使用理由、再現性。

## 8. 残材・廃棄材は鋸刃厚に依存しない固定境界で分類する

- 状態：現行
- 判断内容：切断後の残り0mmを`used_up`（使い切り）、1～50mmを`scrap`（廃棄材）、51mm以上を`remnant`（発生残材）とする。境界値50mmへ鋸刃厚を加算しない。今回の必要部材に使用できなくても、51mm以上なら発生残材とする。
- 採用理由：鋸刃厚によって51～53mm等の分類が変わる不整合をなくし、現場の固定境界を候補評価と表示へ一貫して反映するため。
- 却下した案：廃棄判定境界へ鋸刃厚を加える案、表示層だけで分類を補正する案。
- 影響範囲：残材分類、候補評価、計算結果、JSON、Web表示、HTML出力。

## 9. V1.0.1の入力上限を実務上の計算単位へ合わせる

- 状態：現行
- 判断内容：次の上限をPythonモデル、フォームPOST、HTML、JavaScriptの端末JSON読込で共通使用する。

| 項目 | V1.0.1 |
|---|---:|
| 必要部材 | 1～20行 |
| 在庫残材 | 0～10行 |
| 必要部材1行の本数 | 1～500本 |
| 在庫残材1行の本数 | 1～500本 |
| 在庫新品材本数 | 0～500本 |
| 新品母材長 | 1～6100mm |
| 必要部材寸法 | 1～6100mm |
| 在庫残材寸法 | 1～6100mm |
| 鋸刃厚 | 0～100mm |
| 左端捨て切り寸法 | 0～100mm |

独立した必要部材合計1,000,000本制限は設けない。入力構造上の最大値は20行 × 500本 = 10,000本である。

- 採用理由：公開版V1を実務で扱う材料・設備の範囲へ限定し、誤入力、過大な処理時間、メモリ消費、HTTP本文肥大化を抑えるため。上限を超える対象は材質・規格・保管場所・作業単位などで分割して計算する。
- 却下した案：上限なし、非常に大きな理論上限を公開版の正式上限として維持する案、通常利用目標を別の入力上限として設ける案。
- 影響範囲：Pydanticモデル、フォームPOST、HTML属性、動的入力行、端末JSON読込、境界値テスト。

任意文字入力は、件名20文字、材料種類30文字、データ製作者30文字、備考400文字を上限とし、Pythonの文字列長で判定する。

### 廃止済みの入力上限判断

開発途中には、寸法最大1,000,000mm、鋸刃厚・左端捨て切り最大10,000mm、在庫新品材・在庫残材1行最大100,000本、必要部材合計最大1,000,000本を採用していた。また、合計1,000本程度を通常利用目標としていた。

これらは公開版V1.0.1で実務上の想定範囲へ縮小・整理したため、現在の入力制限ではない。「通常利用目標」も独立した仕様値としては使用しない。

## 10. アプリバージョンとJSON形式バージョンを分離する

- 状態：現行
- 判断内容：アプリバージョンは`1.0.1`、JSONの`format_version`は`1.0`とする。アプリの修正と、JSONデータ構造の互換性変更を別々に管理する。
- 採用理由：互換性を保ったパッチリリースでJSON形式バージョンまで不要に変更せず、読込可否を明確に判断するため。
- 却下した案：アプリのパッチ更新ごとに`format_version`も同じ値へ更新する案。
- 影響範囲：FastAPIアプリ情報、JSON出力、端末JSON読込、HTML出力、テスト。

## 11. 管理番号は計算成功時に発行し、端末出力間で共有する

- 状態：現行
- 判断内容：`Asia/Tokyo`の日時を使い、計算成功時に`NEST-YYYYMMDD-HHMMSS-XXXX`形式で管理番号を発行する。`XXXX`は紛らわしい文字を除いた英大文字と数字から生成する。入力未変更なら識別情報を維持し、入力変更後の再計算では再発行する。JSONとHTMLは同じ管理番号を使用する。
- 採用理由：サーバー保存へ依存せず計算結果と複数出力を対応付け、時刻とランダム文字列により同時利用時の衝突可能性を抑えるため。
- 却下した案：JSONとHTMLへ別番号を付ける案、出力のたびに再発行する案、サーバー保存済み件数から連番を採る案。
- 影響範囲：画面上の識別情報、ファイル名、JSON、HTML、端末JSON読込。

端末JSON読込との互換性のため、旧形式`NEST-YYYYMMDD-NNN`も検証対象として受け付ける。

### 廃止済みの採番判断

初期のサーバー保存方式では、保存日の日本時間とサーバー上の同日最大連番から`NEST-YYYYMMDD-NNN`を採番し、上書き時は番号を維持していた。サーバー保存撤去に伴い、現在の計算成功時採番へ置き換えた。

## 12. 利用者データをサーバーへ永続保存しない

- 状態：現行
- 判断内容：サーバーは計算とリクエスト処理中のメモリ内JSON・HTML生成だけを行い、入力、計算結果、JSON、HTML、履歴を永続保存しない。JSONとHTMLは利用者端末へ直接ダウンロードする。
- JSON読込：ブラウザのFile APIで端末ファイルを読み取り、ファイル本体をサーバーへ送信しない。保存済み計算結果は表示へ再利用せず、入力を復元して再計算する。
- 採用理由：件名、材料情報、担当者、備考、計算結果等が含まれ得るため、公開版V1ではサーバーが利用者データを保持しない境界を明確にするため。
- 却下した案：旧保存経路を互換機能として残す案、将来のデータベース化に備えて保存層だけを残す案、端末JSONファイルをサーバーへアップロードする案。
- 影響範囲：Web API、画面操作、出力、端末JSON読込、キャッシュ制御、ログ、テスト。

### 廃止済みのサーバー保存判断

初期版では、プロジェクト内`data/`へJSONとHTMLを正式保存し、保存一覧、上書き、再ダウンロード、`RecordStorage`を提供する判断を採用していた。

公開版V1への移行時、旧保存UI・APIと端末直接出力が混在して利用者に誤解と意図しないサーバー保存を生じさせたため、旧UI、旧API、保存一覧、上書き、再ダウンロード、`RecordStorage`、アプリからの`data/`参照を完全撤去した。旧方式はV1.0.1の現行機能ではない。

## 13. 公開版V1はCloud Run上で最小限の公開防御を適用する

- 状態：現行
- 判断内容：本番コンテナをCloud Runで実行し、HTTPS終端はCloud Runを使用する。`APP_ENV=production`ではFastAPIの`/docs`、`/redoc`、`/openapi.json`を公開しない。
- 検索除外：画面と出力HTMLへ`noindex, nofollow, noarchive`を設定し、`robots.txt`でもクロール拒否を示す。`robots.txt`は認証やアクセス制御の代替とはしない。
- HTTP応答：基本セキュリティヘッダーを付与し、画面等のHTMLレスポンス、JSON・HTML出力、検索除外応答、受信エラーへ適切な`Cache-Control: no-store`を設定する。ルート固有の既存ヘッダー値を優先する。
- 採用理由：開発時のAPI確認性と既存出力を保ちつつ、本番公開時の不要な情報露出、検索登録、ブラウザ保持を抑えるため。
- 却下した案：開発環境でもAPI文書を無効化する案、`robots.txt`だけをアクセス制御として扱う案、未設計のCSP等を同時導入する案。
- 影響範囲：FastAPI初期化、ミドルウェア、HTML head、`robots.txt`、本番コンテナ、公開設定テスト。

## 14. HTTPリクエスト本文をアプリ側でも制限する

- 状態：現行
- 判断内容：HTTP本文上限は既定64KiB（65,536バイト）とし、`MAX_REQUEST_BODY_BYTES`へ1以上のASCII十進整数を設定した場合だけ変更可能とする。未設定・空文字は既定値、不正設定は起動時エラーとする。
- 防御方式：有効な単一`Content-Length`が上限を超えれば受信前に413とし、ヘッダーの有無や申告値にかかわらずASGIで実際に受信した本文もチャンクごとに累積判定する。不正な`Content-Length`は400とする。
- 採用理由：Cloud Run側の制限とは別に、アプリが扱うフォーム・出力リクエストを早期かつ実受信量に基づいて制限するため。
- 却下した案：`Content-Length`だけを信用する案、本文全体を先読みして複製する案。
- 影響範囲：HTTP受信、環境設定、400・413応答。計算値、行数上限、JSON形式には影響しない。

## 15. 公開版V1の機能を凍結する

- 状態：現行
- 判断内容：V1.0.1で確認済みの計算、画面、JSON・HTML入出力、非永続データ取り扱い、公開設定を公開版V1の機能境界とし、原則として新機能を追加しない。
- 許可する変更：必要な不具合修正、誤認や作業ミスを防ぐ既存表示の修正、セキュリティ修正、公開環境で判明した問題への対応、既存仕様を保証するテスト・文書修正、依存関係・実行環境の必要最小限の保守。
- 採用理由：受入済みの機能とデータ非保持方針を安定させ、公開後の変更を品質維持に必要な範囲へ限定するため。
- 却下した案：公開版V1へ利便性機能や新しい計算・保存・入出力方式を継続追加する案。
- 影響範囲：変更判断、レビュー、テスト、公開運用。
