# Nesting1D 仕様・設計判断記録

## 2026-07-26：チェック1で確定した仕様

### 1. 左端捨て切り寸法
- 判断内容：利用者が変更可能、初期値10mm。入力値と鋸刃厚1回分を新品母材・既存残材の両方で消費する。
- 採用理由：現場条件に対応しつつ標準値を明確にするため。
- 却下した案：10mm固定。
- 影響範囲：入力検証、使用可能長、残材判定、切断手順、テスト。
- 将来見直す条件：材料種別ごとの値が必要になった場合。

### 2. 在庫モードの新品母材長
- 判断内容：保有新品母材と追加購入新品母材は同じ長さとし、入力は1種類。既存残材は寸法ごとに異なる長さを入力可能。
- 採用理由：初期版の入力と計算を明快にするため。
- 却下した案：複数種類の新品母材、保有材と購入材への別々の長さ入力。
- 影響範囲：在庫入力、候補生成、追加購入数、結果JSON。
- 将来見直す条件：複数種類の新品母材対応時。

### 3. 候補内最少母材本数
- 判断内容：数学的完全最適は保証しない。探索で生成した候補中、母材使用本数が最も少ない候補を優先。同数ならパターン数、寸法変更回数の順に減らす。文書では「候補内最少母材本数」と表現する。
- 採用理由：実用的な探索時間を保ち、完全最適との誤解を避けるため。
- 却下した案：完全最適保証、パターン集約のため候補内最少本数を超える案。
- 影響範囲：候補生成・比較、結果説明、再現性、テスト。
- 将来見直す条件：探索方式変更、または許容増加本数を設定可能にする時。

### 4. 入力上限
- 判断内容：寸法最大1,000,000mm、鋸刃厚・捨て切り最大10,000mm、1行最大100,000本、必要部材・既存残材は各最大1,000行、合計必要本数最大1,000,000本。通常利用目標は合計1,000本程度。
- 採用理由：異常な処理時間・メモリ消費を防ぎ、通常利用へ余裕を持たせるため。
- 却下した案：上限なし、通常利用目標を上限とする案。
- 影響範囲：入力モデル、検証、エラー、境界値・性能テスト。
- 将来見直す条件：実測性能または利用実績から調整が必要な時。

### 5. 日時と管理番号
- 判断内容：`Asia/Tokyo` を使用。初回保存日の日本時間で、同日既存番号の最大値+1を採番。同名なら再確認して次番号を採番。初回保存だけ新規採番し、上書きでは維持。JSONとHTMLは同じ番号。
- 採用理由：現場の日付と一致させ、重複を避け、出力間の対応を維持するため。
- 却下した案：UTC日付、保存ごとの再採番、形式ごとの別番号。
- 影響範囲：保存、ファイル名、JSON・HTML、保存テスト。
- 将来見直す条件：複数利用者・プロセスの同時保存対応時。

### 6. 在庫モードの候補優先順位
- 判断内容：必要部材の充足、追加購入新品母材数の抑制、既存残材活用の順。残材使用で追加購入数が増えるなら使わない。追加購入数が同じなら既存残材を多く使う候補を優先し、その後は保有新品、追加購入新品の順。基本表示順は「使用可能な既存残材→保有新品母材→追加購入新品母材」。
- 採用理由：充足と購入抑制を守りながら残材を活用するため。
- 却下した案：追加購入数が増えても残材を必ず使う案。
- 影響範囲：候補評価、材料一覧、切断手順、追加購入数、テスト。
- 将来見直す条件：評価重みを設定可能にする時。

### 7. 使用不能な既存残材
- 判断内容：数値として正しい残材が捨て切り後に必要部材を1本も切り出せなくても全体をエラーにしない。未使用在庫とし、未使用理由を表示。0以下、文字、小数、上限超過は入力エラー。
- 採用理由：正当な在庫情報を保持し、計算可能な材料で処理を継続するため。
- 却下した案：使用不能残材が1件でもあれば全体を拒否する案。
- 影響範囲：入力検証、在庫分類、未使用理由、結果JSON、テスト。
- 将来見直す条件：在庫の事前整理を必須にする時。

### 8. 将来の許容本数設定
- 判断内容：初期版では候補内最少母材本数からの増加を許容しないが、将来変更可能な余地を残す。
- 採用理由：初期版を単純にし、将来の段取り優先運用へ備えるため。
- 却下した案：初期版から許容本数を入力する案。
- 影響範囲：候補比較、将来の設定・スキーマ。
- 将来見直す条件：母材追加と段取り削減の交換条件を指定する要望が生じた時。

### 9. 寸法変更回数
- 判断内容：同一パターン内部は異なる寸法数−1、初回設定は含めず、使用回数も掛けない。パターン間は前パターン末尾と次パターン先頭が異なる場合に1回加算する。実施順を変更回数が少なくなるよう決定し、同点順を固定する。
- 採用理由：同一パターンをまとめて加工する現場運用を反映するため。
- 却下した案：使用回数を掛ける案、初回設定を含める案、パターン間を無視する案。
- 影響範囲：候補比較、実施順、結果モデル、再現性テスト。
- 将来見直す条件：パターンをまとめて加工しない運用へ変わる場合。

### 10. 在庫モードの同点候補と使い切り
- 判断内容：充足、追加購入新品母材数、使用既存残材本数、既存残材からの切出合計長、使用後の既存残材合計長、新規残材の分散抑制、パターン数・寸法変更回数、固定決定順の順に比較する。残り0mmは残材・廃棄材に含めず `used_up`（使い切り）とする。
- 採用理由：既存残材を実質的に多く消費し、小残材を分散させず大きな再利用可能残材を確保するため。
- 却下した案：使用残材本数だけで同点とする案、残り0mmを廃棄材とする案。
- 影響範囲：在庫候補比較、残材分類、結果モデル、例6・7、回帰テスト。
- 将来見直す条件：残材価値を長さ以外の指標で評価する場合。

### 11. 未使用在庫の材料区分と理由
- 判断内容：未使用在庫へ`source_type`を持たせ、`existing_remnant`と`held_new_stock`を区別する。必要部材充足後は`NOT_NEEDED`、残っている必要部材を捨て切り後に1本も切れない場合だけ`NO_REQUIRED_PART_FITS_AFTER_TRIM`、使用により追加購入数が増えるため不採用の場合は`NOT_SELECTED_TO_AVOID_EXTRA_PURCHASE`とする。
- 採用理由：未使用材料の種類と未使用になった原因を利用者が誤解なく確認できるようにするため。
- 却下した案：必要数が0の材料を寸法不足として扱う案、画面側で理由を推測する案。
- 影響範囲：計算結果の`unused_inventory`、在庫結果画面、理由コード回帰テスト。
- 将来見直す条件：未使用在庫へ識別番号や材料固有情報を持たせる場合。
- 非影響範囲：候補生成、候補比較、母材割り当て、追加購入数、完成数、パターン集約、残り0mmの`used_up`。

### 12. 初期版の正式保存と端末ダウンロード
- 判断内容：正式保存はプロジェクト内`data/`限定でJSONとHTMLを保存し、成功時だけ保存済みとする。端末向けJSON・HTMLダウンロードはコピー取得とし、保存済み判定を変更しない。File System Access APIは初期版で採用しない。アプリ内の破棄を伴う操作は保存・破棄・キャンセル、ブラウザ離脱は標準確認を使用する。
- 採用理由：管理番号、競合回避、安全な置換をサーバー側で保証しつつ、PC・スマートフォンへコピーを取得可能にするため。
- 却下した案：利用者によるサーバー絶対パス入力、ブラウザダウンロードだけを正式保存とする案、初期版のFile System Access API。
- 影響範囲：保存層、Web API、画面、未保存状態、`data/`のGit除外、保存・出力テスト。
- 将来見直す条件：PWA化、対応ブラウザ限定の端末ファイル保存、専用Dockerボリュームへ移行する時。
